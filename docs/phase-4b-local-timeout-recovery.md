## Effective timeout finding and evidence

The consultant's finding is reproduced: a function with `SET statement_timeout='100ms'` completed a 400ms sleep in **413ms**. A separate `SET LOCAL` before the outer call stopped it in **153ms** with SQLSTATE **57014**. Its write rolled back; a separate connection confirmed execution ended and no transaction write lock remained.

PostgreSQL starts its statement timer at the outer protocol command. A function's setting alone does not establish that deadline. [PostgreSQL 17 timeout semantics](https://www.postgresql.org/docs/17/runtime-config-client.html).

The smallest supported solution here uses **existing PostgREST handling**, with no new endpoint, broad privilege or timeout migration: PostgREST applies role settings and hoists allowed function settings in a separate transaction-configuration statement before its main RPC statement. [PostgREST 14 transaction sequence and hoisting](https://docs.postgrest.org/en/v14/references/transactions.html#hoisted-function-settings).

Fresh hosted metadata shows **PostgREST 14.18**, PostgreSQL 17.11, `authenticated.statement_timeout=8s`, and `authenticator.statement_timeout=8s`/`lock_timeout=8s`. No hosted setting changed. The existing role defaults already provide the supported configuration; **no role ALTER is presently required**. Function hoisting is supported by this version, but the actual hosted RPC/config-cache behavior is still a native acceptance gate. [Supabase role settings/reload guidance](https://supabase.com/docs/guides/database/postgres/timeouts).

An actual official, SHA-256-verified **PostgREST 14.18 Windows binary** was run locally against disposable PostgreSQL, not a mock HTTP server. Final combined-run results:

| Probe                                          | Result                                         | Independent evidence                                                              |
| ---------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------- |
| Hoisted function 100ms / non-lock sleep 600ms  | 57014 in **114ms**                             | No inserted row, active RPC or transaction write lock                             |
| Role 150ms / function without timeout          | 57014 in **156ms**                             | Same rollback/end checks                                                          |
| Contended row lock, 100ms lock timeout         | 55P03 in **110ms**                             | RPC insert rolled back; no RPC lock/execution; holder separately rolled back      |
| Driver read timer 40ms / server deadline 700ms | Client returned while SQL was still **active** | Independent observer then confirmed the statement ended and its write rolled back |

These tests distinguish **lock timeout** (each lock acquisition), **statement timeout** (server execution of an outer statement), **gateway timeout** (HTTP infrastructure, not measured here) and **client abort/read timer** (the caller stops waiting). The existing three-second function lock settings can bound lock waits; they are not a total RPC budget. Existing 10-second SDK/12-second browser deadlines do not prove SQL stopped. Eight seconds is an execution setting, not a guaranteed end-to-end response time.

**Hosted configuration/rollback scope:** first run one approved temporary 100ms RPC probe and independently inspect counts/activity. Do not increase sleeps or repeat conflicts after a hang. If effective settings disagree, stop and inspect the cache/configuration. A separately approved `NOTIFY pgrst,'reload config'` can refresh role settings. Only if metadata drift is found would the proposed scope be `ALTER ROLE authenticated SET statement_timeout='8s'; NOTIFY pgrst,'reload config';`; rollback restores the exact captured prior value (or RESET if absent), then reloads configuration. No database-wide change, restart, authenticator alteration or arbitrary cancellation API is proposed. No such SQL was executed.

## Recovery tool: implemented behavior and limits

- **One snapshot:** one READ ONLY REPEATABLE READ connection captures catalog, row counts, all nine application/private tables, migration history, required Auth data, original Vault ciphertext and portable app-secret values. Cursors fetch one row at a time. All content comes from that same MVCC snapshot; there are no independent dumps. ACCESS SHARE table locks prevent DDL during capture, while concurrent data writes remain possible and excluded consistently. Freeze key rotation/other administrative changes for capture. The concurrency test committed an extra patient after snapshot acquisition; its patient and audit were absent from the restored snapshot.
- **Explicit scope:** Auth users/identities and Auth audit history are durable capture tables. Every Auth table is classified; unknown tables fail. Live sessions, refresh tokens, login/MFA challenges, flow state, one-time/OAuth authorization state and SCIM tokens are inventoried but omitted. User confirmation/recovery/reauthentication token values are cleared during initial export; clinical historical timestamps and identity/credential hashes are preserved. Restored identities require fresh sign-in. No live session is copied or treated as recovered authentication.
- **Deliberate compatibility limits:** nonempty MFA factors/recovery codes, WebAuthn, SSO/OAuth/custom-provider/SCIM configuration and Auth instances fail closed because provider/origin/encryption dependencies are not proven portable. They are not silently discarded. Required durable serial/identity sequences, foreign-key cycles, partitions/foreign/materialized tables, unknown schemas/tables, unsafe logging/auditing, external-job extensions or nonempty Storage also fail. Current native inventory has 27 Auth tables and only the refresh-token sequence; actual durable-data fit is still unverified. The refresh sequence is inventoried and intentionally not copied because its live tokens are omitted. No nontransactional `setval` is used. [PostgreSQL sequence rollback limits](https://www.postgresql.org/docs/17/functions-sequence.html).
- **Manifests:** table/column/constraint/index/PK/trigger definitions, function owners/definitions/ACLs/search paths, custom role attributes/memberships, schema grants, RLS/policies, exact Auth schema-version contents, reviewed migration hashes/history, extension versions, table counts and canonical row hashes. Missing tables, rows, secrets, links or manifest endings fail. Metadata is compared to a pre-prepared target; SQL/DDL from the archive is never executed. Generated columns are recomputed and checked. JSON text carries large integers and timestamp precision without JavaScript numeric/date conversion.
- **Encryption:** versioned chunked AES-256-GCM; fixed scrypt N=32768/r=8/p=1, 32-byte random salt, 256-bit derived key, fresh 64-bit nonce prefix plus bounded 32-bit frame counter, 128-bit tags. AAD binds header, counter, size and prior tag. Authenticated completion includes stream/table hashes and counts. Wrong passphrase, tampering, truncation, repeated/reordered frames and missing/trailing completion fail. GCM verification precedes yielding each plaintext chunk. This is custom framing using standard primitives, locally tested, not an external cryptographic audit. [Node 22 crypto API](https://nodejs.org/docs/latest-v22.x/api/crypto.html).
- **Bounded handling:** 1MiB maximum encrypted record, 512KiB row bound, 64-table inventory, 100,000 restore artifacts, one million archive frames, 32KiB private stdin, and scrypt maxmem 64MiB. Data rows/secrets are streamed; total data size is not held in RAM. Buffers/derived keys are cleared where practical; JavaScript strings/OS memory are not guaranteed erasable. Only encrypted incomplete/final files are written. SIGINT/SIGTERM request cleanup; hard process death can leave an encrypted `.incomplete-*` file for inspection, not a plaintext staging file.
- **Target safeguards:** explicit different project ref, trusted postgres direct/session endpoint, verified TLS, private connection input and explicit isolation confirmation. Connection-string/unknown-field overrides are rejected. Target must have compatible native schemas/extensions and all six reviewed migrations already prepared, matching Auth schema versions, identical owner/grant/RLS/function metadata and matching migration history. All clinical/Auth/Vault data must be empty; prepared migration/platform history is the explicit exception. Data-table exclusive locks precede a fresh emptiness check. No active app traffic/external jobs/signup; operator attestation and metadata checks are both required.
- **Native re-encryption:** call target `vault.create_secret` inside the restore transaction. Preserve original codes/HMAC key/digests, clinical/Auth IDs, request IDs, reasons and historical timestamps. New Vault storage UUIDs are explicitly mapped in a temporary table and an **encrypted mapping receipt**. Issuance receipts receive mapped UUIDs only at their initial insertion. Original ciphertext stays in the encrypted archive for provider-assisted recovery; it is not INSERTed into restricted native Vault tables. No root access/change and no source history rewrite.
- **Security verification:** app-owned user triggers are temporarily disabled only on the empty target and restored to their exact prior modes before comparison/commit. FK/internal triggers and RLS are never disabled. Unknown Auth user triggers fail. Final canonical row hashes, counts, native-API secret hashes/HMAC/reference checks and complete security metadata must match. Ordinary roles still cannot read reference digests/Vault or assume the executor. SQL bind parameters and generic database-side insert/rewrap error wrappers avoid secret literals/error details; unsafe server logging configurations fail preflight.
- **Atomicity and failure:** all restore data, temporary function/table creation, Vault writes and trigger changes share one transaction. `verifyOnly:true` checks everything then ROLLBACKs. Real commit follows a flushed encrypted mapping receipt. SQL rollback must be acknowledged before reporting confirmed rollback; otherwise status requires target inspection. A lost COMMIT response is explicitly **unknown**, and a subsequent receipt-publication failure is explicitly **committed but receipt pending**. Keep the encrypted prepared mapping receipt, inspect target independently, and never blindly rerun. Filesystem publication and DB COMMIT cannot be one atomic transaction. Target schema/project preparation is outside this transaction and separately approved; the tool neither provisions nor resets it.

Operator connections set effective **10s server statement/1s lock/60s idle transaction/15min transaction** limits at startup, before statements; a separate 12s driver read deadline bounds waiting. A network/client timeout still requires independent inspection before retry. The root-import tool is unchanged, explicitly **uncleared**, and never called by this workflow.
