## Exact proposed migration — approval required

File: **`supabase/migrations/20261021210732_doctor_draft_workflow.sql`** (filename generated by the installed Supabase CLI).

SHA-256: `D0CD71D1F1CA295E9E3C7AD82BF406C596DE2C08BBA250409C40C3455F20C6E0`.

Purpose: make the patient/header/ordered-items save atomic through ordinary user-scoped PostgREST RPC calls, with retry safety and stale-write protection.

1. Add nullable UUID `prescriptions.draft_request_id` and a unique partial index. Grant authenticated **SELECT/INSERT on that new column only**; no digest/status/issuance grant is added. The existing RLS remains authoritative.
2. Add `prescription_items.sort_order` (`smallint`, default 0, check 0–29), with authenticated INSERT on that column. Existing table-level SELECT already covers item columns. No new UPDATE privilege is needed; a draft's item replacement occurs within the save transaction.
3. Add `public.save_doctor_draft(uuid,jsonb,jsonb,text,uuid,timestamptz)`, **SECURITY INVOKER**, fixed `search_path=''`. It requires `current_user='authenticated'`, current active doctor membership and the existing live-session helper; derives doctor UUID from `auth.uid()`. It validates SQL inputs independently of TypeScript. New saves insert the patient (if needed), draft header and all items in one transaction. Edits lock only an owned `draft` row and check exact `updated_at`; item replacement and notes/patient selection are atomic.
4. Add `public.delete_doctor_draft(uuid,timestamptz)`, also **SECURITY INVOKER** with the same authorization and fixed search path. It locks only an owned draft and rejects stale versions before deleting the header/cascading items.
5. Explicitly revoke RPC execution from PUBLIC/anon/service_role; grant execution only to authenticated. Merely being authenticated is insufficient: both functions enforce live active-doctor authorization internally and retain RLS/column checks.

There are **no new security-definer functions, policies, tables, role assignments, privileged keys or authentication configuration changes**. Existing RLS, immutability triggers and digest protections remain. Existing migrations are byte-identical to the prior phase hashes.

The create request token is not a prescription/dispensing reference. Advisory transaction locking serializes the same doctor's concurrent create retries. Identical retries return the already-saved draft; reuse with different content is rejected. Unchanged edit retries return the current version, while stale differing edits/deletes are rejected. Idempotency applies while that draft record exists: it is not a permanent tombstone service for requests after an explicit deletion. A fresh new-draft page has a new token; intentionally submitting a separate new form can create another record.

The hosted **dry run only** listed exactly this pending migration; nothing was applied remotely. No reset/reseed/schema replacement, history repair, account reprovisioning, paid-plan change, deployment or Git push was performed.
