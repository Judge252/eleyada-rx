## Reference/key inventory

| Material | Location / purpose | Provisioning |
|---|---|---|
| `al_eyada_rx.lookup.v1` | Vault secret, 32 CSPRNG bytes encoded as 64 lowercase hex; HMAC-SHA-256 lookup key | Separately approved trusted operator runs `supabase/operations/provision_lookup_key_v1.sql` on the independently verified target. Generates inside PostgreSQL; fails if name already exists. Never replace a used version. |
| `al_eyada_rx.reference.<prescription UUID>` | One encrypted Vault secret per issuance, format `RX1-K1-…`; recovery artifact UUID in receipt | Created atomically by trusted issuance boundary, never manually pre-generated or displayed in a report. |
| Supabase project Vault root key | Provider-managed key outside the database, encrypts Vault records | Never put in app env/source. Approved custodian must establish encrypted offline escrow before relying on recoverable issued references. |
| Escrow passphrase / operator access token | Independent custodian password manager / transient operator memory | Never source, app configuration, shell arguments, logs or chat. Separate from encrypted backup and database dump. |

`RX1` is reference format v1, `K1` is lookup-key version 1. Twenty DB CSPRNG bytes encode to 32 Crockford Base32 symbols (160 bits); uppercase ASCII normalization removes only ASCII spaces/hyphens and rejects confusables, Unicode, invalid length/alphabet/version. HMAC input is domain-separated and includes format/key version. Unique digest constraint; only digest collisions retry, at most three attempts. Other unique conflicts return PT409. Raw code/digest generation is never client-controlled. Digest alone cannot recover a reference; encrypted recovery plus root-key custody is essential.
